# 博客文档写作规则

## 文章结构

- **概念先行**：开篇第一段直接定义核心概念或背景，不寒暄、不铺垫。先让读者知道"这篇讲什么"，再展开细节。
- **标题是精炼的知识点**：不是提问，不要把用户提问的内容直白地写出来，而是整理成一个知识点展示出来。
- **分层递进，自顶向下展开**：按逻辑层次组织章节（如：硬件→固件→内核，或：概念→机制→边界情况），每层先给全局视角（系统在做什么、为什么分支），再展开细节（具体函数、变量、条件）。不要自底向上让读者从细节拼图。
- **孤零零的知识点不应挂在某节末尾**：如果一段内容只在为另一个章节提供前提/背景，它应该融合到那个章节里，而不是孤零零地附在当前章节末尾。读者在当前章节看不到它的关联性，读到目标章节时又已经忘了它。
- **知识点之间要有因果衔接**：多个相关知识点不能孤立堆叠，必须用过渡句串联成因果链。如"A是什么 → A在哪里被用 → 那条路径何时触发 → 触发后什么行为"，每步自然引出下一步，不要让读者自己补逻辑跳跃。陈述结论或要求时同样要附一句原因（如"需要 BBML，否则多核下其他核可能踩空或踩错内存"），不要只给结论不解释为什么。
- **检视前向依赖**：如果前文内容依赖后文才能理解（依赖性引用），应调整文档顺序，把被依赖的内容前移；如果只是"详见后文第X节"的指向性引用，则合理，不需要调整。
- **交叉引用**：行内链接到自己其他博文提供上下文，格式如"具体逻辑可以参考[这里](链接)"。

## 图解规范

- **图是易读的**：重构后图片要尽可能保留。不要随意修改 plantuml 图的源码（可能渲染失败）。
- **图片编号联动**：图片放置顺序如果修改的话，有编号的图片，编号也得修改，正文中有提到引用了这个图片的话，正文提及的编号也要修改。
- **按场景选择图解工具**：
  - **ASCII art**：数据结构布局（队列、ring buffer、ROB）、内存布局、简单的调用树（`+->` 树形）
  - **PlantUML**：状态机、时序图、流程图、组件关系图
  - **HTML 动画**：交互式演示（如 TLB 多命中动画、JS 交互演示）
- **时间序列图**：分析并发/竞态/状态变迁时，用连续多张图展示同一对象在不同时间点的状态（如"操作前" vs "操作后"、"正确执行" vs "错误执行"），让读者直观看到状态如何变化。
- **每个抽象概念配一个具体例子**：概念讲完立刻给一个具体的图或代码示例。

## 代码规范

- **真实代码**：用实际内核/库代码，标注源文件路径（如 `/* linux/arch/arm64/kvm/arm.c */`）。
- **禁止写行号**：不要在代码引用中写行号（如 `[kvm_main.c:721]`），行号会随版本变化失去意义，用函数名或上下文定位即可。
- **调用栈精简**：调用栈只在首次出现或层级切换时标注一次源文件路径，不要每行都重复写代码路径，太啰嗦。
- **注释驱动分析**：代码块内用前缀注释标注自己的分析（如 `/* n: ... */`）。
- **问题独立成节**：代码展示后，用 `XXX问题:` 作为子节标题单独分析（如"CAS问题"、"ABA问题"）。
- **调用栈格式统一**：涉及跨层调用栈（如 KVM 场景包含 QEMU/kernel/KVM/host）时，调用树节点前加 `[QEMU]`、`[kernel]`、`[KVM]`、`[host]` 等层级标志。缩进统一用 2 空格（不用 tab，tab 宽度在不同渲染器下不可控），箭头统一用 `+->`（`+` 表示有子节点），不用 `->` 或 `→`。
- **校验调用栈**：写完调用栈后，根据实际代码逐层校验调用关系是否正确，不要凭记忆臆造调用链。
- **commit message 辅助推理**：对某段代码逻辑有疑问时，先用 `git log` / `git show` 查看相关 commit message，理解 patch 的真实意图，再结合代码路径推理。不要只盯着代码本身猜测。
- **解释与代码对应**：解释代码时，正文中提及的函数/变量必须在展示的代码块中可见。引用代码块中未出现的符号（如调用者、被调用者）时，先补充调用链上下文，不要凭空抛出读者无法定位的符号。
- **诚实标注不确定性**：用 `(?)`、`(to check)`、`todo:` 标记未确认的内容，不要假装确定。

## 语言风格

- **意简言骇，讲重点**：不写废话，不重复陈述同一观点，不铺陈已知背景。每个段落只讲一件事，能用一句话说清的不用两句，能省略的过渡句一律省略。
- **行文要说人话**：不要把多个函数名、变量名、条件判断堆叠在一句话里当过渡句。技术术语之间要有动词和逻辑词衔接，让读者像读正常句子一样能顺下来。如果一句话里出现超过三个技术名词，拆成多句。
- **英文术语附中文名**：首次出现英文技术术语时，附上中文名（如"Translation Fault（缺页）"），不要只写英文让读者自己猜中文对应。后续重复出现时可只用英文。
- **过渡段只做过渡**：知识点之间的过渡段只交代衔接关系（如"PERMS掩码用在 stage2_pte_needs_update() 中"→引出后续），不展开变量定义、分支条件等细节。细节留给对应的章节自然展示，避免信息过载和与后文重复。反面示例：过渡段写了"返回 false → -EAGAIN → 延迟到 relax_perms 处理"，后文又完整展开同一机制——重复了，应合并到后文一处。
- **不要自行发明名词**：使用标准术语，不要创造"软件收口"这类非标准表述。如果需要描述一个概念，用已有的技术术语或用人话直白描述。
- **加粗要精准**：关键的地方加 **加粗**，但不能频繁地加，物极必反。
- **设问自答**：行文中自然设问再回答，引导读者思考（如"怎么做这个识别？"随后分析）。
- **建模思维**：把实际问题抽象成模型（如分支预测→0/1序列，无锁队列→三指针），用模型解释机制。
- **零自我汇报**：从不说"本文将..."、"之前写了..."，直接进入内容。改了啥就是啥，静默修改，不要在正文中汇报"你之前是 X，现在改成 Y"。

## Markdown 格式

- `- ` 列表如果连续多行，第一个 `- ` 前面必须加一个空行，否则不会自动换行，会紧贴前面的文字。
- `> ` 引用块要实现换行的话，两行之间必须插多一个 `> `（空引用行），否则不会换行。
- spec/标准文档的引用（ARM规则 ID、SMMU spec 章节等）不要把英文原文整段堆在正文里。正文中只写：**粗体规则 ID** + 一句话中文要点（括号注明"原文见附录X"）；英文原文 + 中文翻译统一收录到文末"附录"（附录A = ARM规则索引，附录B = SMMU spec 索引），每条格式：`**规则ID** — 主题（spec章节）` + blockquote（英文原文 + 中文翻译）。附录中收录完整原文，不做截断。
- 正文行文不要大段大段地堆叠文字。多个想法挤在一段里时：
  - 要么拆成 `- ` 分点列表（每点只讲一件事，如果依然有内容冗余，可以加个二级的 `-`，以此类推，分级沉淀一大段描述）
  - 要么压缩成一句话；超过两句话的解释就应该考虑分点。
  - spec 引用、代码块、表格、图不属于"大段堆叠"。

## 文档修改与重构

- **动态插入**：新内容要整理清楚文章逻辑，思考应该在哪一个位置添加哪些内容，动态插入到文档中，而不是无脑地添加到文章末尾。
- **尊重用户调整**：如果用户对之前 Accept 的内容做了手动调整，先确认修改是否正确。如果正确，下次写入时以用户修改后的版本为准，不自作主张改回；如果发现问题，提醒用户让用户自己决定。
- **合并重复**：文章中有多处重复的内容，整理总结成一处，然后找到最合适的位置去写。

### 重构流程

1. 遍历全文，总结最好的文档结构，内容分阶段说明。
2. 写或改文件前先通读，找到各处冗余重复的内容，整理总结合并成一处，然后找到最合适的位置去写。
3. 保证内容完整，逻辑合理，方便阅读。
4. 如果重构到后面的章节，review 后发现有一些内容应该合并到前面，需要更新插入到前面的内容中。

## 交互式 HTML 动画

交互式 HTML 动画（如 PlantUML 动图、JS 交互演示等）不要放在 `_posts/` 的 post 资产文件夹里——hexo 内置 `html → html` 直通 renderer，会把 `.html` 文件当作独立文章处理（标题为空 → 显示为 "[Untitled Post]"）。正确做法：在 `source/` 根目录下创建独立文件夹（如 `source/tlb-multihit/index.html`），并在 `_config.yml` 的 `skip_render` 中添加该目录（如 `- tlb-multihit/**`），让 hexo 原样复制不渲染——否则 hexo 会用主题模板包裹 HTML（注入 header/footer/JS），iframe 里会看到 Author/License 等主题元素。iframe 用绝对路径引用（如 `src="/tlb-multihit/index.html"`）。参考 `source/buddy-animation/` + `skip_render: - buddy-animation/**` 的结构。
