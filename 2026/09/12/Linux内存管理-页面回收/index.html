内存不够用了,内核敢抢谁的页?凭什么抢这一页而不是那一页?抢之前要不要跟正在用它的进程打个招呼?进程下次访问被抢走的页,又会发生什么?

这四个问题覆盖了页面回收(Page Reclaim)子系统的全部主干。本文基于主线内核 v7.3-rc 的代码,以一个匿名页的一生为主线把答案串成完整的故事线。《深入理解 Linux 内核》第 17 章的框架依然成立,但实现早已换代:page 变成了 folio,zone 让位给 node,还添了 MGLRU 和 DAMON 两员新将。

一、页的身份证:struct folio

一切从"内核怎么描述一个物理页"开始。老书里的 struct page 还在,但回收路径的代码如今全部操作它的封装 struct folio。区别在于 folio 可以代表一整块复合页:透明大页 THP 一次管 2MB,如果还按 4KB page 逐个处理,一个页要重复处理 512 次。folio 把"这一摞页"当成一个整体,这是大页时代的必然选择。

回收只关心 folio 里的几个字段,按用途分三组:

两个引用计数值得记住一辈子:

  • _refcount 是页面的命根子。它统计所有持有这个页的引用(进程映射、页缓存、内核临时引用),归零页面就死亡,归还伙伴系统
  • _mapcount 是页面的幸福指数。它只统计有多少个用户态 PTE 映射到这个页,-1 表示无人映射。回收前必须把它降到 -1,这就是反向映射要解决的事

mapping 字段还有个"抠位"技巧:anon_vma 和 address_space 都是 4 字节对齐的指针,最低两位必然为 0,内核用最低位当类型标签,1 是匿名页,0 是文件页,一个布尔量白捡。第二章会看到这个标签怎么用。

二、页与进程的契约:反向映射

回收一个页之前,必须把所有指向它的 PTE 清掉,否则进程还在通过旧映射访问已释放的内存,读到的是被复用的垃圾数据。

难点在于:物理页不知道谁在用它。页表里只有"虚拟地址到物理页"的正向记录,反着查没有索引。暴力解法是扫描所有进程的所有页表,几 GB 内存配几百个进程,天文数字。

内核的解法是登记户口,而不是挨家搜查。匿名页出生时,把包含它的 vma(进程的一段连续地址区间)登记进 anon_vma;要找映射时,先查户口本拿到 vma 列表,再从每个 vma 的页表根走到具体 PTE。vma 的数量比 PTE 少好几个数量级。

anon_vma_chain(avc) 是图里的枢纽,一头连 anon_vma,一头连 vma。fork 之后父子进程共享匿名页,每个进程的 vma 各挂一条 avc 到同一个 anon_vma 上,找到任何一个就能顺藤摸瓜找到全部。

执行清除的是 try_to_unmap(),它顺着 rmap 对每个 PTE 调用 try_to_unmap_one(),里面有个体现"良心"的检查:发现 PTE 的 AF 位是 1(刚被访问过),立即放弃这页,返回失败。回收者绝不动热页。

顺带一个 ARM64 细节:PTE 里的 DBM 是硬件维护的映射级脏位,清映射时它会被汇集到 folio 的软件级 PG_dirty 标志上。第四章的写盘判决读的是后者。

三、冷热分离:LRU 与第二次机会法

户口有了,接下来的问题是:挑谁?依据是局部性原理:很久没人访问的页,将来被访问的概率也小。

内核给页排队的方式是 LRU 链表,而且按"匿名/文件"和"活跃/不活跃"分成 4 条,外加一条不可回收链表:

链表不再挂在 zone 上,而是挂在 lruvec 上:每个 NUMA 节点的每个 memcg 各有一套。这样容器(cgroup)之间互不偷页,谁的内存超了就收谁的。

冷热怎么判断?靠 folio 的两个标志位 PG_referenced 和 PG_active 组成的两位计数器。硬件在进程访问页时自动置 PTE 的 AF 位,内核定期收割这些 AF 位折算成软件标志。判断规则是第二次机会法,像缓刑制度:第一次被抓(被访问)不处决,清掉标记放回,再犯才处理。

为什么两次才升级?设想一个每小时写一次日志的进程,如果一次访问就标热,它会永远霸占 active 链表。两次访问确认的是"近期反复使用",这才是热的确凿证据。

真正做判决的函数是 folio_check_references(),它综合 PTE 的 AF 收割结果和软件标志,给出三值判决:

情况 判决 去向
无任何引用,AF 全 0 RECLAIM 进入回收流程
匿名页有引用,或可执行文件页有引用 ACTIVATE 升回 active
文件页第一次被引用 KEEP 留在 inactive,下次再判

逐条拆解:

三个环节值得展开。

匿名页为什么必须写盘? 因为匿名页在磁盘上没有备份,内存里这份就是唯一原件。直接丢掉的话,进程不会收到友好报错,要么缺页后拿到一个清零的空页,数据悄悄消失,要么读到被复用的垃圾数据,静默损坏。干脆杀进程重开也不行,以网络服务为例,连接全断、缓存全冷、十几 GB 的模型重新加载,重启代价极高。

swap 的答案是:把冷匿名页抄一份到磁盘再释放内存,进程真要用时缺页异常自动取回,只是慢一点,状态一个不少。AgentENV 沙箱用的是同一个思想:沙箱里跑了几小时的环境(激活的 conda、加载的十几 GB 模型),直接销毁再重建代价不可接受,所以快照时把内存状态落盘、恢复时 mmap 装回。用磁盘 I/O 换进程状态的完整保留,swap 就是内核里这套机制的自动化版本,区别只是粒度:AgentENV 快照整台虚机,swap 只搬冷页。

PG_dirty 判决的两条路。folio_test_dirty() 置位后,文件页和匿名页待遇完全不同:

  • 脏文件页:回收路径不负责写回(内核 v6.19 起,commit "mm: vmscan: simplify the logic for activating dirty file folios" 改掉的老行为),只打 PG_reclaim 标记放回 LRU,交给 writeback 子系统的 flusher 线程,下轮扫描发现干净了再直接丢。回收线程绝不能被磁盘速度拖死
  • 脏匿名页:pageout() 只是提交写请求就返回,__swap_writepage() 发 bio 写 swap 区,I/O 完成后回调 end_swap_bio_write() 收尾。全流程异步化

页槽去哪了? 换出后 PTE 不能浪费,ARM64 上 Valid 位清零让描述符变无效,触发 Translation Fault(缺页异常),剩余位存 swp_entry_t(swap 区号 + 页槽号)。一个 64 位字既当地址又当失踪去向登记条,零额外内存开销。

没有 swap 会怎样?get_scan_count() 里的 can_reclaim_anon_pages() 发现 swap 余量为 0 就只扫文件链表,匿名页全部跳过,压力全砸在文件页缓存上,挤干之后来的就不是回收而是 OOM Killer。

五、谁扣扳机:三个入口与水位

流水线随时待命,问题是何时启动。答案藏在水位里,像水库的三条刻度线:

  • 高水位:内存充裕,kswapd 睡觉
  • 低水位:空闲页跌破此线,wakeup_kswapd() 叫醒后台清洁工,它一路回收到高水位才睡,避免频繁醒睡抖动
  • 最小水位:留给紧急分配的保命水,跌破此线直接回收都可能不够,就要请 OOM Killer 了

六、二十年演进:书里的老朋友去哪了

老书基于 2.6 时代的代码,对照 v7.3,思想未变,骨架已换:

旧(2.6 时代) 新(v7.3) 为什么改
struct page struct folio 大页时代逐 page 处理太碎
per-zone LRU per-node + per-memcg lruvec NUMA 与容器隔离
两位计数器 LRU + MGLRU 按代分代 扫描开销更低, 冷热更准
只能释放或 swap + demotion 降级到慢速内存层 DRAM + CXL 多层硬件
被动等水位 + DAMON 主动监控 冷热检测与回收解耦
回收路径写回脏文件页 v6.19 起只打标记等 writeback 回收线程不被磁盘拖死

两句展开最值得记的两个:

MGLRU(Multi-Gen LRU)把"两个状态位"升级成"多个世代"。页按访问时间归入不同代,年轻代留在内存,年老代优先回收,判定冷热不再靠两次访问的启发式,而是直接看它落在第几代。struct lru_gen_folio 里最多维护 4 代,开启后传统 LRU 链表闲置。

DAMON 不再被动等水位,而是主动巡逻:把地址空间切成区域,每个区域只抽样一个页的 AF 位代表整体,按访问模式动态合并拆分区域。冷得彻底的区域直接交给 reclaim_pages() 回收,配合 kdamond 内核线程,把"找冷页"和"收冷页"两件事彻底解耦。

终章:一个匿名页的一生

现在让前面所有机制在一个页身上依次发生。这是全文的检验:能不看文章讲完这个故事,就真的学会了。

诞生。进程第一次写一个匿名 mmap 区,缺页异常走进 do_anonymous_page(),分配新页,建立 PTE,folio_add_lru() 把它挂上 inactive 匿名链表。此刻它 _mapcount 为 0,PG_active 和 PG_referenced 都是 0,一个刚出生的冷页。

服务期。进程频繁读写它,硬件自动置 PTE 的 AF 位。回收扫描时 folio_referenced() 收割 AF 位,第一次访问置 PG_referenced,第二次访问 folio_mark_accessed() 把它升级进 active 链表。它是热页,没人动得了它。

老化。进程转向别的工作,很久不碰这个页。它从 active 头部慢慢沉到尾部,shrink_active_list() 一刀把它降回 inactive,PG_workingset 打上"曾经热过"的标记。它开始排队等待审判。

换出。内存吃紧,流水线找上了它。folio_alloc_swap() 在 swap 区订一个页槽,folio_mark_dirty() 标记必须写盘,try_to_unmap() 清掉 PTE(脏位 DBM 汇集到 PG_dirty),pageout() 异步写入 swap 区,I/O 完成回调收尾,页框归还伙伴系统。PTE 里 Valid=0,剩余位记着它去了哪个页槽,一张失踪登记条。

仓库。它躺在 swap 区的页槽里,不占一字节内存,只有 PTE 里那串编码记得它。

换入。某天进程又访问那个虚拟地址,Valid=0 触发 Translation Fault,do_swap_page() 从 PTE 解析出 swp_entry_t,先查交换缓存(可能别人已取回,白捡),没有则 swapin_readahead() 顺带预读相邻 8 页,新页框填好数据,PTE 重新指回内存,反向映射重新登记。进程恢复执行,仿佛无事发生,只是慢了一点。

总结

  • _refcount 是命根子,_mapcount 是幸福指数,回收的全部前提都在这两个计数器里
  • LRU 的两位计数器是缓刑制度,两次访问才升级,一次访问只留标记,防的是偶尔被摸一下的页霸占内存
  • 回收判决读 PG_dirty,不读 PTE 的 DBM,清映射时硬件脏位才汇集到软件标志上
  • 文件页丢了有原版,匿名页丢了就是丢了,所以 swap 不是可选项而是匿名页的保命机制,AgentENV 快照与它同构,都是用磁盘 I/O 换状态保留
  • 水位是水库的三条刻度线,跌破低水位叫醒 kswapd,跌破最小水位才轮到 OOM Killer,中间隔着整套回收机制在工作 ```
