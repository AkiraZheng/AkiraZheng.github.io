热迁移（Live Migration，在线迁移）要把一台运行中的虚机从源服务器搬到目的服务器：内存、vCPU 状态、设备状态一样不落，业务还几乎不中断。同时满足这两条的可行策略只有"先全量、后增量"：虚机继续跑，QEMU 先把整个内存搬一遍，之后只补变化过的页；等变化量小到一次短暂停机能发完，才让虚机停机，补上最后一轮脏页和设备状态，再在对端拉起。

整个策略成立的前提，是源端能准确回答一个问题：上一轮拷贝之后，虚机又改了哪些页？把"页被写过"这个事件记录下来的机制叫脏页跟踪（dirty logging），arm64 KVM 上的经典实现就是本文的主角 dirty bitmap（脏页位图）模式：KVM 给每个 memslot（内存插槽）维护一张"每 4KB 页一个 bit"的位图，靠 stage-2（第二阶段翻译表）写保护把 guest 的写变成 Permission Fault（权限错误），在 fault 处理里往位图置位，QEMU 周期性把位图同步回用户态、发送对应脏页、再让 KVM 清位并重新写保护，循环直到收敛。

一句话讲清楚为什么需要标脏：热迁移的停机窗口由"停机那一刻还剩多少脏页"决定，而"还剩多少脏页"只能靠持续标脏来知道。

开篇思考题，全文读完应能回答：

  1. 虚机全程不关机，QEMU 凭什么知道某个页在上一轮发送之后又被 guest 改写了？
  2. 开启脏页跟踪的那一次 KVM_SET_USER_MEMORY_REGION，KVM 为什么可以不把整个内存一次性写保护？不写保护怎么保证不漏记？
  3. 同样是 stage-2 只读的页，KVM 怎么区分"我为标脏写保护的页"和"本来就只读的页"？guest 写这两种页，后续路径有什么不同？
  4. stage-2 写保护只能拦住 guest 发起的写，QEMU 自己（设备模拟 DMA）往虚机内存写数据时，谁来标脏？

代码取自主线 Linux（约 7.3）与 openEuler QEMU 8.2。写 fault 到 stage-2 权限的微观机制（relax_perms、BBM）在读写权限篇里已拆过，本文直接引用结论；写权限的事实源（VMA（虚拟内存区域）与 memslot）在写权限下传篇；VFIO 设备自身的迁移在VFIO 热迁移篇。

1. 热迁移三阶段：全量、增量、停机收尾

先看迁移对象。QEMU 把要搬的东西注册成一串 SaveStateEntry（保存状态项），分两类：

  • RAM：注册名 "ram" 的迭代式 handler，占迁移量的大头，有 save_setup / save_live_iterate / save_live_complete_precopy 三个阶段回调
  • 设备状态（VM State）：每个设备一份 VMStateDescription（设备状态描述符），只在停机后一次性序列化。几个真实的例子：
    • GIC（Generic Interrupt Controller，通用中断控制器）的 vmstate_gic，含 ctlr、每中断的 enabled/pending/active/level、irq_target、priority 等
    • vCPU 的 vmstate_arm_cpu，含 xregs[32]、pc、cpsr、elr_el[4]、系统寄存器对、generic timer
    • passthrough 设备的内部状态走 VFIO 迁移协议，MMIO（Memory-Mapped I/O，内存映射 IO）BAR 空间本身不参与脏页跟踪（详见 VFIO 篇）

vCPU 寄存器平时在 KVM 里，停机后由 cpu_synchronize_all_states() 从 KVM 拉回 QEMU，再随 vmstate 一起发。

再看流程。qmp_migrate 解析 URI 后 migrate_init 复位状态，异步连上目的端，连接成功回调 migrate_fd_connect 里创建名为 "live_migration" 的迁移线程：

整个热迁移由 migration_thread 驱动，分三段（图1）：

  • setup 段：发流头（MAGIC/VERSION），调 qemu_savevm_state_setup()，然后状态从 SETUP 切到 ACTIVE。对 RAM 来说这一步做三件事：
    • 初始化 QEMU 侧位图
    • 通知 KVM 开启脏页跟踪（第 3 节）
    • 做首次位图同步（第 5 节）
  • 迭代段：主循环每轮执行 migration_iteration_run()，先估剩余量，够小就转停机，否则 qemu_savevm_state_iterate() 发一轮脏页
  • 收尾段：migration_completion() 停机并发出剩余数据，migration_iteration_finish() 处理源端虚机的最终状态

停机切换的判定条件是"剩余量小于阈值"。阈值不是写死的字节数，而是带宽乘停机预算：

downtime_limit（停机时间上限）默认 300ms。也就是说：当"剩余脏页量"小到按当前带宽 300ms 内能发完时，虚机才停机，进入最后的停机拷贝。migration_completion_precopy() 里 migration_stop_vm(RUN_STATE_FINISH_MIGRATE) 让所有 vCPU 停下，业务中断从这里开始，到目的端 vm_start() 结束，这段时长就是迁移的 downtime（停机时间）。

如果脏页产生速度持续高于发送带宽，迭代永远收敛不了。precopy（预拷贝，即先全量后增量的模式）的对策不是强制停机，而是压脏页速率：migration_bitmap_sync 里每隔 1 秒评估一次，连续两个周期脏量超发送量就触发 auto-converge（自动收敛，动态限制 vCPU 运行时间比例，mig_throttle_guest_down() 周期性让 vCPU 睡觉截流）或 dirty-limit；仍然不收敛就等用户 cancel 或切 postcopy（后拷贝，先停机切换、缺页再按需拉取的模式）。

迭代阶段的四个动作（同步位图、发送脏页、清除已发送块、写 fault 标脏）覆盖了 dirty bitmap 模式迭代期的全部环节。下面按生命周期逐个拆开。

2. dirty bitmap 模式：一句话与三层位图

一句话定义：QEMU 给 memslot 打上 KVM_MEM_LOG_DIRTY_PAGES 标记，KVM 为它维护一张每 4KB 页一个 bit 的位图；页面被写保护后，guest 一写就 Permission Fault 陷到 EL2，KVM 在 fault 处理里给位图置位；QEMU 周期性用 ioctl 把位图同步回用户态，发送对应脏页，再让 KVM 清掉这些位并重新写保护，如此循环直到收敛。

这里要分清两种陷入，触发机制完全不同：

  • guest 的写触发 Permission Fault，是硬件异常：CPU 退出 guest 进入 KVM 的异常处理路径（VHE 布局下宿主内核本身就运行在 EL2），一次标脏就是一次这样的异常陷入加处理
  • QEMU 同步位图走 KVM_GET_DIRTY_LOG / KVM_CLEAR_DIRTY_LOG，是宿主机系统调用：陷入宿主内核里的 KVM 模块，与 guest 异常无关

所以"trap 到 EL2 获取脏页位图"的说法不准确：位图的读写都走宿主内核的 ioctl 路径，只有置位动作走 guest 异常退出的 fault 路径。

位图在系统中实际存在三层（图2），职责各不相同：

  • KVM memslot 位图是脏页记录的唯一来源，只有写 fault 和 KVM 内部写 guest 内存的路径会置位
  • QEMU 全局位图 ram_list.dirty_memory[] 按 ram_addr 编址，有 VGA/CODE/MIGRATION 三种 client，KVM 同步来的位和 QEMU 设备模拟 DMA 写置的位（第 7 节）都汇到这里
  • RAMBlock.bmap 是迁移专用消费视图，同步时从全局位图搬运而来，发送线程用它找脏页，发一页清一位

数据单向流动，不回流。看内核侧的数据结构：

位图的定位规则极简：bit 下标 = gfn - memslot->base_gfn。64GB 内存的虚机是 16M 个页，位图 2MB。分配有个历史包袱，kvm_alloc_dirty_bitmap() 一次 __vcalloc(2, dirty_bytes, ...) 分配两倍长度：第二份是 legacy 模式 KVM_GET_DIRTY_LOG 做"快照+清零"时的暂存缓冲，避免在 ioctl 里 vmalloc。manual-protect 模式（下文）用不到第二份，但分配照旧。

渐进模式的正确性依赖一个不变量：位图里的 1 是"至少这么脏"的下界。开启时全 1 是最保守的估计（全部重发，冗余但不丢）；之后每次 CLEAR 把"已确认发送"的位清零并写保护，未发送的位保持 1。这个设计来自 2020 年的 arm64 补丁 "KVM: arm64: Support enabling dirty log gradually in small chunks"。

两个边角问题。KVM_MR_CREATE（新建 slot 时就带 LOG_DIRTY）为什么不写保护：新 slot 的 stage-2 映射必然为空（映射只由 slot 内的 fault 按需建立），wp 对空区间是 no-op，真正的保证来自 fault 路径，即 logging 下强制 4K 粒度、读 fault 不给写权限（第 4 节）。迁移结束关闭 LOG_DIRTY 时走 else 分支，只释放 eager split 缓存，没有任何 unprotect 动作，原因见第 8 节。

4. 写 fault 标脏：权限真值表与三层判定

迭代期里 guest 的写随时可能撞上写保护。以渐进模式为例，某个页被 CLEAR 写保护后，guest 再写它：stage-2 PTE（Page Table Entry，页表项）的 S2AP_W 为 0，MMU 报 Permission Fault，FSC（Fault Status Code，错误状态码）为 0x0C|level，硬件把异常路由到 EL2，KVM 接手：

权限怎么算？写权限篇讲过事实源有两层（VMA 与 memslot），fault 时刻现算成枚举。v7.3 的实现在 kvm_s2_fault_compute_prot()，核心就一行条件：

memslot_is_logging() 的定义是 memslot->dirty_bitmap && !(flags & KVM_MEM_READONLY)。展开成真值表：

  • 不在 logging（没开迁移）：写权限恒给，正常 RW 映射
  • logging + 读 fault：给 RO。这一行决定了标脏如何触发：读 fault 建的映射不带写权限，guest 随后的写必然再 fault 一次，那次 fault 才拿到 W 并标脏
  • logging + 写 fault：给 RW 并标脏。kvm_s2_fault_map() 尾部 if (writable && !ret) mark_page_dirty_in_slot(...) 完成这一次标脏
  • device（VM_PFNMAP 且非内存 PFN）旁路 logging 检查直接给 W，避免设备映射反复 fault；不过这类 VMA 在 kvm_arch_prepare_memory_region() 里直接拒绝开 LOG_DIRTY（-EINVAL），所以正常配置下走不到

怎么区分"本来就只读的页"和"为标脏写保护的页"？ 这是同一张 PTE 上的两种 RO，硬件位（S2AP_W=0）完全同形，区分全部在软件层，共三层判定：

  • QEMU 侧：只读 MemoryRegion（如 ROM）注册 memslot 时同时带 KVM_MEM_READONLY 与 KVM_MEM_LOG_DIRTY_PAGES 两个 flag（kvm_mem_flags() 两个判断互不干扰），位图照常分配
  • 内核 logging 判定：memslot_is_logging() 把 READONLY slot 排除在脏页跟踪外，位图虽在，fault 路径不再据它收权，也就不标脏
  • fault 入口分流：kvm_handle_guest_abort() 里 gfn_to_hva_memslot_prot() 返回的 writable 只看 READONLY flag。写 fault 落在真只读 slot 上时 write_fault && !writable 成立，走 io_mem_abort() 以 KVM_EXIT_MMIO 退出给 QEMU 模拟，根本进不了标脏路径；写 fault 落在写保护页上时 writable 为真，进 user_mem_abort() 放权加标脏

所以两类只读页的命运分岔在 fault 入口之前：真只读页的写 fault 永远出不来（每次都当 MMIO 丢给用户态），写保护页的写 fault 在 KVM 内闭环。这个区分是软件意图，不是硬件属性，PTE 不需要也不能承载它。

写 fault 闭环的另一半是粒度。stage-2 平时为了性能用 2M/1G block 映射，而位图是 4K 粒度：一个 2M block 只有一位可记，block 里任意一页写过整块都得算脏，跟踪粒度被放大 512 倍。所以 logging 下 kvm_s2_resolve_vma_size() 强制 max_map_size = PAGE_SIZE，block 必须拆：

  • eager split（预拆分）：KVM_CAP_ARM_EAGER_SPLIT_CHUNK_SIZE 显式开启（默认 0 关闭），开启时在 CLEAR 的批处理路径 kvm_mmu_split_huge_pages() 里提前把 block 拆完
  • lazy split（惰性拆分）：不开启时，写 fault 落在 2M RO block 上，mapping_size(4K) 不等于硬件报的 perm_fault_granule(2M)，走 kvm_pgtable_stage2_map() 换粒度重建，fault 的那个 4K 以 RW 落位并标脏，其余 511 个子页留 invalid 等各自的 fault

最后补一个 v7.3 的新变化：stage2_set_prot_attr() 现在对可写 PTE 无条件置上 DBM（Dirty Bit Modification，bit 51）。这个位与 S2AP_W 并存，但只有在 VTCR_EL2.HD=1（FEAT_HDBSS 硬件脏位，第 9 节）时才参与硬件行为；经典 bitmap 模式下 HD=0，DBM 是惰性位，权限判定只看 S2AP。也就是说，没有 HDBSS 硬件时，arm64 的标脏就是纯软件的"写保护 + Permission Fault + fault 路径置位"，stage-2 没有软件可直接读取的硬件脏位。relax_perms 恢复写权限的原子修改与 BBM 细节，见读写权限篇第 7、8 节。

5. 位图同步：QEMU 拉取 KVM 位图

标脏发生在 KVM，消费发生在 QEMU，中间需要周期性搬运。QEMU 8.2 的 precopy 路径里，同步（sync）只发生在三个时机（postcopy 切换前的 ram_postcopy_send_discard_bitmap 另有一次，不在本文范围）：

  • 首次：ram_init_bitmaps() 开启跟踪后立即一次
  • 迭代中：每轮 migration_iteration_run() 先调 qemu_savevm_state_pending_estimate() 做估值，只用上次同步留下的计数，零开销；估值降到 threshold_size 以下才调 qemu_savevm_state_pending_exact()，RAM 的 ram_state_pending_exact() 在此刻真正做一次同步：
  • 停机后：ram_save_complete() 里 migration_bitmap_sync_precopy(rs, true)（last_stage 模式），随后把剩余脏页一次发完

这个两级设计（estimate/exact）是 8.2 相对老版本的变化：

  • 老版本每轮 ram_save_iterate() 开头都同步一次
  • 新版本把同步挪到收敛判定处，全量发送（bulk）阶段（剩余量远大于阈值）根本不同步
  • 原因是同步不便宜：每次都要对每个 memslot 做一次 GET ioctl，legacy 模式下还伴随整槽清零、重新写保护与 TLB flush，而积压很大时同步结果不改变任何决策

ram_save_iterate() 里那句 "in case it was the 1st time and we had to sync the dirty bitmap" 的旧注释是老设计的残迹。

同步的完整链路：

内核侧 GET ioctl 的行为按模式分岔：

kvm_arch_sync_dirty_log() 在 arm64 平时是空函数（HDBSS 开启时 kick 所有 vCPU 逼它们退出 guest 排空硬件脏位缓冲，第 9 节）。

legacy 模式那四步的顺序不是随手排的，内核注释写明了正确性论证：

  1. Take a snapshot of the bit and clear it if needed.
  2. Write protect the corresponding page.
  3. Copy the snapshot to the userspace.
  4. Upon return caller flushes TLB's if needed.

Between 2 and 4, the guest may write to the page using the remaining TLB entry. This is not a problem because the page is reported dirty using the snapshot taken before and step 4 ensures that writes done after exiting to userspace will be logged for the next call.

翻译过来：步骤 2 清了 PTE 的写权限，但各 pCPU 的 TLB（Translation Lookaside Buffer，地址翻译缓存）里还缓存着"可写"的旧表项，flush 生效之前 guest 的写不会 fault，这些写不进位图。这段窗口的写由步骤 1 的快照兜底（先快照后写保护，窗口内的写在快照里已经是 1）；flush 之后的写必然 fault，记入下一轮。flush 是"脏页不丢失"的时间边界。

arm64 的这个 flush 不需要向各 vCPU 发 IPI（核间中断）请求，kvm_arch_flush_remote_tlbs_range() 由调用 CPU 同步执行范围 TLBI（TLB Invalidation，TLB 失效指令）：

底层是 tlbi ipas2e1is，按 IPA（中间物理地址，即 guest 物理地址）范围失效 stage-2 表项，超出 MAX_TLBI_RANGE_PAGES 的分块执行，每次配 dsb(ish)。is 后缀（Inner-Shareable）意味着指令本身硬件广播到所有核，返回 0 让通用层的 KVM_REQ_TLB_FLUSH 请求路径短路，所以 arm64 全树 grep 不到这个 request 的使用者。

manual 模式把 GET 简化成"纯读"，清零、重保护、flush 三个动作全部转嫁给 CLEAR ioctl，也就是发送路径。这正是第 6 节的内容。

6. 先清后发：发送脏页与 CLEAR 重保护

发送侧的循环在 ram_save_iterate() 里，每轮在限速预算内反复调 ram_find_and_save_block()：

发送以 host page（宿主机页，THP（Transparent Huge Page，透明大页）大页时一页 = 512 个 target page（目标架构页，虚机视角的页））为单位：pss_host_page_prepare() 圈定大页边界，循环把页内所有脏 target page 逐个清位发送。原因在 CLEAR 的代价：一次 CLEAR 会把范围内的大页全部拆成 4K 重新写保护（见下），整页发送让一次拆分服务整页的所有子页，避免对同一大页反复拆分。

核心是"先清后发"的顺序，migration_bitmap_clear_dirty() 的注释直说了理由：

This must be called before we send any of the page in the chunk because we need to make sure we can capture further page content changes when we sync dirty log the next time.

展开讲，"清"有两层，顺序都是先于发送：

第一层：清 QEMU 消费位图（test_and_clear_bit(page, rb->bmap)）。先清再发，发送之后发生的重新标脏才能在下一轮 sync 把这一位重新点亮，页被重发；如果发完才清，就会把"发送窗口内新产生的脏"连同旧位一起抹掉。

第二层：清 KVM 位图并重新写保护（这就是"拷贝到对端之后如何写保护"的答案）。不直接逐页发 ioctl，而是用 clear_bmap 做"推迟+分块"：sync 搬运全局位图进 rb->bmap 时，clear_bmap_set() 对整个 RAMBlock 的所有块置标记（默认 2^18 个 target page 一块，即 1GB，一块一位）；标记不区分块里有没有脏页，真正的触发条件是发送，发送块内第一个脏页时 migration_clear_memory_region_dirty_bitmap() 测试并清除该标记，命中才对整块发起远端清除：

推迟到发送时刻、切成 GB 级块，是把 CLEAR（伴随写保护、拆大页、TLB flush 的昂贵操作）从 sync 时点分摊到发送过程中。继续往下到 KVM：

kvm_physical_log_clear() 开头有个重要分支：manual protect 未启用时直接 no-op 返回，legacy 模式下 GET 已经"快照+清零"过整张位图，用户态不需要再显式清。kvm_log_clear_one_slot() 传给内核的位图有讲究：对齐扩展出的首尾空洞必须清零，慢路径干脆构造一张临时位图，只回放已从内核同步到 QEMU 的脏位。内核注释警告了不这么做的后果：把尚未同步的位也清掉，guest 的修改就会从位图里丢失，迁移后目的端直接数据损坏或 panic。

内核侧 CLEAR 的处理：

atomic_long_fetch_andnot 的语义保证正确性：只清用户点名、且确实为 1 的位。GET 之后 fault 新置的位若不在用户同步过的快照里，CLEAR 的 mask 不含它，位保持 1，留给下一轮 GET。

把一页的完整生命周期串起来（渐进模式），状态随时间的演变如下表：

时刻 发生了什么 KVM 位图的位 stage-2 权限 QEMU bmap 的位
t0 开启跟踪 1（初始全 1） RW（渐进模式不整体写保护） 1（初始全 1）
t1 bulk 发送推进到 P 所在块 1 RW 1
t2 发送 P：先 CLEAR 再读页内容 0（CLEAR 清位） RO（CLEAR 写保护） 0（发送前清位）
t3 guest 写 P 1（fault 置位） RO，触发 fault 0
t4 fault 处理完成 1 RW（relax_perms 放权） 0
t5 下一轮 sync 1（GET 拷出） RW 1（重新点亮，等待重发）

t2 到 t3 之间就是"先清后发"要保护的窗口：CLEAR 先把 P 写保护，QEMU 随后读页内容发送。这期间 guest 的写要么发生在读之前（内容已带上），要么触发 fault 重新置位，下一轮 sync 后重发。两个顺序（KVM 侧"先清位再写保护最后 flush TLB"，QEMU 侧"先 CLEAR 再发送"）共同保证了任何时刻的写都不会丢失记录。

7. 旁路：QEMU 自身写虚机内存的标脏路径

第 4 节的写 fault 路径有个盲区：stage-2 只约束 guest 经 IPA 发起的访问。QEMU 用户态（设备模拟）直接经 HVA（Host Virtual Address，宿主机虚拟地址）写 guest RAM 时根本不经过 stage-2 翻译，KVM 的写保护形同虚设，位图也看不到这些写。迁移期间这类写真实存在：e1000/virtio 设备模型把网络包 DMA 进 guest 内存、VGA 刷新显存，都是 QEMU 进程在写自己的 mmap。

谁来标脏？QEMU 自己的地址空间层。所有设备模型写 guest 内存都走 address_space_write()，写完顺手置位：

invalidate_and_set_dirty() 先用 memory_region_get_dirty_log_mask() 确认当前有哪些 client 在跟踪（迁移期间含 MIGRATION 位），再按 mask 置全局位图。这些位与 KVM 同步来的位在第 5 节的 sync 处汇合：ramblock_sync_dirty_bitmap() 的 qatomic_xchg 把全局位图整体搬进 rb->bmap，不区分来源。

另外两条 QEMU 视角的写路径：

  • vhost（内核态数据面）：vhost 的写发生在内核，不经 QEMU 地址空间，靠 vhost 自己的 log 记录；vhost 的 MemoryListener 注册了 .log_sync = vhost_log_sync，在同一轮 sync 里把 log 搬回 QEMU 全局位图
  • TCG 加速（无 KVM 时）：QEMU 的 SoftTLB 对 clean 页的写走 notdirty_write() 标脏，与 KVM 无关，一笔带过

这一节回答了思考题 4，也解释了三层位图里中间那层存在的意义：KVM 位图只覆盖 guest 的写，QEMU 全局位图是 guest 写与 VMM 写的汇合点。

8. 停机切换与两端收尾

停机阶段发的东西：剩余脏页（RAM）加上全部设备状态（vmstate）。QEMU_VM_EOF 是给目的端的结束信号，源端随后置 COMPLETED，migration_iteration_finish() 把源端虚机置为 RUN_STATE_POSTMIGRATE（不再运行，进程通常随后退出）。

目的端在迁移开始前就以 -incoming tcp:0:4444 之类的方式起好了进程，等连接进来：

两个要点：

  • 目的端写页不走 address_space 层，qemu_get_buffer 直接 memcpy 进 block->host + offset，所以不产生 QEMU 侧标脏（也不需要）
  • 位图和页权限都不迁移。目的端从头开跑，没有脏页跟踪；rb->receivedmap 只是收页记录，供 postcopy/resume 场景回传源端重建状态用。源端页表里那些 RO 映射随源 VM 一起销毁，谈不上恢复

真正需要"恢复"的是迁移失败或被取消的场景：源端虚机要继续跑，得停跟踪、还性能。cancel 路径 migrate_fd_cancel() 置 CANCELLING 并 shutdown 迁移流，migration_thread 的 migration_detect_error() 返回致命错误跳出循环，migration_iteration_finish() 对 FAILED/CANCELLED 分支调 vm_start() 恢复源端业务，随后 cleanup 链关跟踪：

内核侧收到 flags 变更（KVM_MR_FLAGS_ONLY，LOG_DIRTY 从有到无）后做两件事：kvm_arch_commit_memory_region() 走 else 分支，只释放 eager split 缓存；位图由 kvm_commit_memory_region() 的 FLAGS_ONLY 分支 kvm_destroy_dirty_bitmap() 释放。除此之外全目录搜不到任何 unprotect 动作，页表里残留的 RO 映射靠惰性恢复：下次 guest 写它触发 Permission Fault，user_mem_abort 里 memslot_is_logging() 已经为假，compute_prot 因 !memslot_is_logging(...) 给回 W，relax 放权；此后新 fault 还能按 VMA 重建 2M 大页。这与姊妹篇的结论一致：写保护只改 PTE 硬件位，从不改软件事实源，所以权限随时可以从事实源重算回来。

9. 模式谱系：bitmap、dirty ring 与 HDBSS

把本文的 dirty bitmap 模式放回谱系里看：

模式 标脏动作 同步方式 arm64 状态
legacy bitmap 写 fault 置位 GET 顺带清零+重保护 可用，老 VMM 路径
manual+initially-set bitmap 写 fault 置位 GET 纯读，CLEAR 清零+重保护 本文主述，QEMU 8.2 默认
dirty ring（脏页环） 写 fault 推环形队列 用户态按 vCPU 读取环，RESET 重保护 7.3 支持
HDBSS 硬件置 DBM+缓冲 IPA VM exit 排空缓冲，sync 前 kick vCPU 7.3 新增，依赖硬件

bitmap 模式的开销瓶颈在同步成本：GET/CLEAR 都按 memslot 整体或大块工作，QEMU 找脏页要 find_next_bit 扫描全内存的位图，开销与脏页数量无关、与内存总量正相关。dirty ring 反过来：每次写 fault 顺带把 {slot, offset} 推进 per-vCPU 的环形队列（kvm_dirty_ring_push()），用户态按队列读取，成本与脏页数成正比。arm64 在 7.3 的支持由两个 Kconfig 组成：

  • HAVE_KVM_DIRTY_RING_ACQ_REL：非 TSO（Total Store Order，全序内存模型）架构用 acquire/release 语义的版本
  • NEED_KVM_DIRTY_RING_WITH_BITMAP：ring 与备份位图混合，因为 vgic/its 这类没有 vCPU 上下文的内核写路径没法推 ring，必须落回位图

QEMU 侧 listener 也二选一：ring 模式注册 log_sync_global（先 kvm_dirty_ring_flush() 再处理），bitmap 模式注册 log_sync。

HDBSS（Hardware Dirty Bit State Save，硬件脏位状态保存）是 v7.3 加入的硬件加速：

  • 开启脏页跟踪时 KVM 自动置 VTCR_EL2.HD，可写映射处于 writable-clean 状态
  • 硬件在写时直接把它提升为 writable-dirty 并把 IPA 记进 per-vCPU 的 HDBSS 缓冲，写不再 fault
  • VM exit 时 kvm_flush_hdbss_buffer() 逐条 kvm_vcpu_mark_page_dirty() 汇入同一套位图

这也是第 4 节 DBM 位被无条件置上的原因：没有 HD=1 时它是惰性位，硬件就绪后同一批 PTE 直接获得硬件标脏能力。对本文流程的影响仅一处：kvm_arch_sync_dirty_log() 在 HDBSS 开启时 kick 所有 vCPU 逼缓冲排空，保证 GET 快照之前硬件脏位都已写入位图。

总结

  1. dirty bitmap 模式的本质是用写权限换脏页记录：KVM 写保护 stage-2 PTE，把 guest 的写变成 Permission Fault，在 fault 处理里给 memslot 位图（每 4KB 页一个 bit，下标 = gfn - base_gfn）原子置位一次。位图是脏页记录的唯一载体，停机窗口由它算出的剩余脏页量决定。
  2. 位图分三层、单向流动：KVM memslot 位图是记录来源（只有 fault 置位），QEMU 全局位图汇合 guest 写与 QEMU 自身 DMA 写（stage-2 管不到后者，invalidate_and_set_dirty 补位），rb->bmap 是发送消费视图（find_next_bit 扫描、发一页清一位）。
  3. arm64 + QEMU 8.2 实际走 manual-protect + initially-all-set 渐进模式：开启跟踪的那次 ioctl 不做整体写保护（位图初始全 1，未保护页的写不置位但位本来就是 1），写保护推迟到发送时逐块 KVM_CLEAR_DIRTY_LOG 完成，配合拆大页把开启停顿摊进首轮全量发送。
  4. 两个顺序保证不丢脏页：内核侧"先快照/清位，再写保护，最后 flush TLB"，写保护与 flush 之间的窗口由快照兜底，flush 之后的写必然 fault 入下一轮；QEMU 侧"先 CLEAR（重保护）后发送"，发送期间的并发写要么进内容要么重新标脏。
  5. 只读页与写保护页在 PTE 上同形，区分全在软件：READONLY memslot 被 memslot_is_logging() 排除在跟踪外，其写 fault 在入口就被分流到 MMIO exit；权限收放都由 fault 时刻从 memslot/VMA 事实源现算，因此关闭跟踪后无需主动恢复写权限，惰性放权即可。
